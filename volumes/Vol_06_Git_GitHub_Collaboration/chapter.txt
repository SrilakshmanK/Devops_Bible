# 🧠 Why Git Matters

You are going to work with:

```text
Bash scripts
Python applications
FastAPI services
Dockerfiles
Terraform
Kubernetes manifests
CI/CD pipelines
configuration
documentation
```

All of these need controlled change management.

Without version control:

```text
file-final
file-final2
file-final-real
file-final-real-v2
file-final-use-this-one
```

With Git:

```text
Commit A
   ↓
Commit B
   ↓
Commit C
   ↓
Commit D
```

You know:

```text
what changed
who changed it
when it changed
why it changed
what the previous state was
```

And importantly:

> Git allows you to experiment without being afraid of losing a known-good state.

# 🧭 Learning Philosophy

## Rule 1 — Understand Git's model before memorizing commands

Don't memorize:

```bash
git add .
git commit
git push
```

as magic commands.

Understand:

```text
Working Directory
       ↓
Staging Area
       ↓
Commit
       ↓
Local Repository
       ↓
Remote Repository
```

---

## Rule 2 — Visualize history

Use:

```bash
git log --graph --oneline --decorate --all
```

and Git Graph in VS Code.

Git becomes much easier once you can **see the commit graph**.

---

## Rule 3 — Learn recovery, not just happy paths

A professional Git user must know what to do after:

```text
wrong commit
wrong branch
bad merge
bad rebase
deleted branch
lost work
accidental reset
wrong push
```

---

## Rule 4 — Git is not GitHub

Understand:

```text
Git
↓
Version control system
```

while:

```text
GitHub
↓
Hosted Git platform + collaboration ecosystem
```

# Chapter 01 — Version Control Fundamentals

## Objective

Understand why version control exists before learning Git.

---

## 1.1 The Problem Without Version Control

Imagine a project containing:

```text
project/
├── app.js
├── app-final.js
├── app-final2.js
├── app-new.js
├── app-new-fixed.js
└── app-use-this.js
```

Problems:

* Which version is correct?
* Who changed it?
* What changed?
* Why?
* Can we restore yesterday's version?
* Can two developers work simultaneously?
* Can we identify who introduced a bug?

---

## 1.2 Manual Versioning

Understand the limitations of:

```text
copy → rename → modify → repeat
```

---

## 1.3 Local Version Control

Understand the idea of storing history locally.

---

## 1.4 Centralized Version Control

Concept:

```text
Developer
    ↓
Central Server
    ↑
Developer
```

---

## 1.5 Distributed Version Control

Git:

```text
Developer A
    ↕
Full Repository

Developer B
    ↕
Full Repository
```

Each clone contains repository history.

---

## 1.6 Git

Understand Git as a:

> Distributed Version Control System.

---

## 1.7 Snapshots

Git conceptually stores project states as snapshots rather than thinking only in terms of "file differences."

Understand this mental model carefully.

---

# Chapter 08 — Rebasing & History Management

## Objective

Understand rebasing rather than treating it as a dangerous command to memorize.

---

# 8.1 Why Rebase?

Suppose:

```text
      D---E
     /
A---B---C
```

Rebase can transform the feature history into:

```text
A---B---C---D'---E'
```

The commits are recreated on a new base.

---

# 8.2 Merge vs Rebase

Understand the difference:

```text
merge
→ preserves divergent history

rebase
→ replays commits onto another base
```

Neither should be treated as universally "better."

Choose based on workflow and repository policy.

---

# 8.3 Rebase Changes Commit IDs

This is critical.

Because commits are recreated:

```text
D
```

becomes:

```text
D'
```

and therefore has a different identity.

---

# 8.4 Interactive Rebase

Learn:

```bash
git rebase -i
```

Use it to understand:

```text
pick
reword
edit
squash
fixup
drop
```

---

# 8.5 Squashing

Understand why several local development commits might be combined before sharing history.

---

# 8.6 Rebase Conflicts

Workflow:

```text
rebase
 ↓
conflict
 ↓
resolve
 ↓
git add
 ↓
git rebase --continue
```

---

# 8.7 Abort

```bash
git rebase --abort
```

---

# 8.8 Golden Rule

Understand the practical principle:

> Be careful rewriting history that other people already depend on.

---

## 🧪 Lab — Git Disaster Drill

### Disaster 1

### Disaster 2

# Chapter 17 — Git Security & Repository Hygiene

## Objective

Learn how Git repositories can accidentally expose sensitive information.

---

# 17.1 Never Commit Secrets

Examples:

```text
.env
API keys
database passwords
private keys
cloud credentials
tokens
```

---

# 17.2 `.gitignore` Is Not Security

This is critical.

If a secret was already committed:

```text
adding it to .gitignore
```

does not automatically remove it from Git history.

---

# 17.3 Secret Removal

Understand conceptually that removing sensitive data from history requires history rewriting or repository-specific remediation.

---

# 17.4 SSH Keys

Never commit:

```text
~/.ssh/id_rsa
~/.ssh/id_ed25519
```

or equivalent private keys.

---

# 17.5 GitHub Secret Scanning

Understand that hosted platforms can detect certain exposed credentials.

Do not rely on detection as your primary defense.

---

# 17.6 Least Privilege

GitHub access should follow:

```text
minimum required permissions
```

---

# 17.7 Signed Commits

Introduction to:

```text
GPG
SSH signing
```

Understand why commit signing can provide stronger authorship verification.

Advanced cryptographic configuration can wait.
