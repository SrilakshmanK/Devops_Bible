# Chapter 01 — What Makes an AI Application Different?

Start by understanding the difference between ordinary software and AI-powered software.

---

## 1.1 Traditional Software

Traditional software is usually:

```text
Input
 ↓
Deterministic logic
 ↓
Output
```

Example:

```python
if age >= 18:
    return "adult"
```

---

## 1.2 AI Software

AI systems often behave more like:

```text
Input
 ↓
Context
 ↓
Model
 ↓
Probabilistic output
 ↓
Validation
 ↓
Application logic
 ↓
Output
```

The output is not guaranteed to be identical every time.

---

## 1.3 New Engineering Problems

AI applications introduce:

* nondeterminism
* hallucination
* prompt injection
* model failures
* token costs
* context limits
* evaluation challenges
* provider dependency
* tool misuse

---

## 1.4 The Important Principle

Never allow:

```text
LLM output
    ↓
direct privileged action
```

without validation and authorization.

Prefer:

```text
LLM
 ↓
Structured output
 ↓
Validation
 ↓
Authorization
 ↓
Application logic
 ↓
Action
```

# Chapter 04 — Prompt Architecture & Prompt Management

Prompts become application code.

Treat them accordingly.

---

## 4.1 Prompt Components

```text
System instructions
+
Application context
+
Retrieved context
+
Tool results
+
User input
```

---

## 4.2 Prompt Templates

Separate:

```text
prompt template
```

from:

```text
runtime data
```

---

## 4.3 Versioning Prompts

Treat prompts like source code.

Record:

```text
prompt version
model
configuration
evaluation results
```

---

## 4.4 Prompt Regression

A prompt change can improve one task and break another.

Therefore:

```text
Prompt change
 ↓
Evaluation suite
 ↓
Compare
 ↓
Deploy
```

---

## 4.5 Prompt Injection

Never insert arbitrary user/document content into trusted instruction sections.

Maintain boundaries:

```text
TRUSTED INSTRUCTIONS

<untrusted_user_input>
...
</untrusted_user_input>
```

---

# Chapter 05 — Structured Outputs & Reliable Data Extraction

LLMs are powerful at generating text.

Applications need structured data.

---

## 5.1 Free-Form Output

```text
John has five years of Python experience.
```

Harder to consume programmatically.

---

## 5.2 Structured Output

```json
{
  "name": "John",
  "experience_years": 5,
  "skills": ["Python"]
}
```

---

## 5.3 Schema

Define:

```text
expected fields
types
constraints
```

Use Pydantic.

---

## 5.4 Validation Pipeline

```text
LLM
 ↓
Structured Output
 ↓
Pydantic Validation
 ↓
Business Validation
 ↓
Application
```

---

## 5.5 Retry on Invalid Output

Conceptually:

```text
LLM
 ↓
invalid
 ↓
repair/retry
 ↓
validation
```

Do not retry indefinitely.

---

## 5.6 Partial Failure

If one field is invalid, decide whether to:

* reject
* repair
* request clarification
* continue with defaults

The decision belongs to application logic.

# Chapter 06 — Tool Calling & Function Execution

This is one of the most important AI application concepts.

---

## 6.1 Tool Definition

A tool has:

```text
name
description
input schema
execution logic
permissions
```

---

## 6.2 Example

```text
get_employee_leave_balance(employee_id)
```

The model can request:

```json
{
  "employee_id": "123"
}
```

But the application decides whether this is allowed.

---

## 6.3 Tool Execution Flow

```text
User
 ↓
LLM
 ↓
Tool Call
 ↓
Validate Arguments
 ↓
Authorize
 ↓
Execute Tool
 ↓
Tool Result
 ↓
LLM
 ↓
Final Response
```

---

## 6.4 Tools vs APIs

A tool can internally call:

* database
* REST API
* Python function
* search engine
* business service

---

## 6.5 Tool Permissions

Example:

```text
read_user_profile
```

may be allowed.

But:

```text
delete_user
```

should require stronger authorization.

---

## 6.6 Tool Idempotency

Some operations can safely repeat.

Others cannot.

Understand the difference before allowing automatic retries.

---

Build five safe tools:

```text

```

Implement schemas and authorization.

# Chapter 08 — State, Memory & Conversation Management

A chatbot is not simply:

```text
question → answer
```

if it supports conversations.

---

## 8.1 Conversation State

Store:

```text
conversation_id
user_id
messages
timestamps
metadata
```

---

## 8.2 Short-Term Context

Recent conversation included in the prompt.

---

## 8.3 Long-Term Memory

Information stored externally.

Examples:

```text
user preferences
previous decisions
application state
```

---

## 8.4 Memory Is Application Data

Do not blindly let the LLM decide what becomes permanent memory.

Use rules.

---

## 8.5 Conversation Summarization

Long conversations can exceed context limits.

Possible strategy:

```text
Old messages
 ↓
Summary
 ↓
Recent messages
 ↓
Current question
```

---

## 8.6 Memory Security

Never allow one user's conversation state to appear in another user's context.

## 10.3 Workflow vs Agent



## 10.4 Agent Components


# Chapter 11 — Agent Loops & Tool-Based Reasoning

## 11.1 Basic Loop

```text
while not finished:

    observe state

    ask model for next action

    validate action

    execute action

    update state
```

---

## 11.2 Maximum Steps

Always establish:

```text
max_iterations
```

Otherwise an agent can loop forever.

---

## 11.3 Tool Failure

A tool can fail.

The agent should receive:

```text
tool_error
```

rather than crashing unpredictably.

---

## 11.4 Observation Size

Do not dump unlimited tool output back into the model.

Limit and summarize where appropriate.

---

## 11.5 Agent State

Track:

```text
goal
steps
tool calls
observations
errors
remaining budget
```

---

## 🧪 Lab

Build a tiny agent with:

```text
calculator
document search
current time
```

Require:

* maximum 5 steps
* schema validation
* tool authorization
* logging

# Chapter 19 — AI Security

This is a major engineering topic.

---

## 19.1 Prompt Injection

Untrusted content may attempt to manipulate the model.

---

## 19.2 Indirect Prompt Injection

Example:

```text
User
 ↓
RAG
 ↓
Document contains malicious instructions
 ↓
LLM
```

The malicious instruction came from a document rather than the user.

---

## 19.3 Tool Injection

A model may attempt to call a tool with dangerous parameters.

Always validate.

---

## 19.4 Data Leakage

Possible sources:

* prompts
* logs
* retrieved context
* conversation memory
* model outputs
* tool results

---

## 19.5 Authorization

Never let the model decide access rights.

Use deterministic application authorization.

---

## 19.6 Output Security

Treat model output as untrusted input if it is later used by another system.

---

## 19.7 Secrets

Never expose:

```text
API keys
JWT secrets
database passwords
cloud credentials
```

to the model unless there is a very deliberate and controlled architecture.
