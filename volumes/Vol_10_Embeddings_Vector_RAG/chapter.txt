# 📘 Volume 10 — Embeddings, Vector Search & RAG

## 🎯 Objective

Learn how AI applications give LLMs access to external knowledge.

By the end of this volume, you should understand and be able to build:

```text
Documents
   ↓
Parsing
   ↓
Chunking
   ↓
Embedding
   ↓
Vector Storage
   ↓
Query Embedding
   ↓
Retrieval
   ↓
Reranking
   ↓
Context Construction
   ↓
LLM
   ↓
Grounded Answer
```

This is the foundation of **Retrieval-Augmented Generation (RAG)**.

The goal is not simply:

> "Build a PDF chatbot."

The goal is to understand **why retrieval works, when it fails, how to measure it, and how to engineer a reliable retrieval system.**

---

# 🧠 Core Mental Model

An LLM has knowledge encoded in its learned parameters.

But your application may need information that is:

* private
* proprietary
* frequently changing
* too large to put directly into a prompt
* specific to one organization
* unavailable during model training

RAG introduces an external knowledge path:

```text
                         ┌──────────────┐
                         │  Knowledge   │
                         │    Base      │
                         └──────┬───────┘
                                │
                         Indexing Pipeline
                                │
                  ┌─────────────▼────────────┐
                  │      Vector Store        │
                  └─────────────┬────────────┘
                                │
User Question ───────► Retrieval
                                │
                                ▼
                         Relevant Context
                                │
                                ▼
                              LLM
                                │
                                ▼
                           Answer
```

The most important principle:

> **RAG is not a model. It is an application architecture.**

# Chapter 01 — Why Retrieval Exists

Start with the problem.

---

## 1.1 LLM Knowledge Has Boundaries

A model may know general information.

But your application might contain:

```text
company policies
private documentation
customer records
internal APIs
product manuals
legal documents
technical specifications
recent events
```

You cannot expect the model's parameters to automatically contain all of this information.

---

## 1.2 The Context Problem

Suppose you have:

```text
10,000 pages of documentation
```

You cannot simply put all of it into every prompt.

Problems include:

* context limits
* latency
* cost
* irrelevant information
* noise
* poor attention allocation

---

## 1.3 Retrieval as Information Selection

Instead:

```text
10,000 pages
     ↓
Search
     ↓
Top relevant passages
     ↓
LLM
```

The LLM receives a much smaller amount of relevant information.

---

## 1.4 RAG vs Fine-Tuning

### Fine-tuning

Changes model parameters.

Useful for:

* behavior
* style
* task specialization
* domain adaptation

### RAG

Provides external information at inference time.

Useful for:

* private knowledge
* changing information
* document question answering
* knowledge bases

---

## 1.5 RAG Is Not Always Necessary

Sometimes normal application logic is better.

For example:

```text
"What is the user's account balance?"
```

This should usually be:

```text
Database query
```

not semantic retrieval.

---

```text

Database query

Fine-tuning
Normal code
Combination
```

Explain every decision.

# Chapter 02 — Embeddings From First Principles

You encountered embeddings in V09.

Now go much deeper.

---

## 2.1 Representation

Computers ultimately work with numbers.

An embedding converts an object into a numerical vector:

```text
Text
 ↓
Embedding Model
 ↓
Vector
```

Example:

```text
"PostgreSQL database"
        ↓
[0.12, -0.38, 0.71, ...]
```

Real embeddings may contain hundreds or thousands of dimensions.

---

## 2.2 Semantic Representation

The objective is to place semantically related items in useful regions of vector space.

Conceptually:

```text
             database
              ●
             ● PostgreSQL
          ● SQL
     
                                  ● mountain
                                  ● climbing
```

The actual geometry is high-dimensional.

---

## 2.3 Embedding Models

Study:

* sentence embeddings
* document embeddings
* query embeddings
* multimodal embeddings

Understand that different embedding models produce different vector spaces.

---

## 2.4 Same Model Requirement

If documents are embedded with one embedding model and queries with an incompatible embedding model, similarity search may not work properly.

---

## 2.5 Dimensions

Understand:

```text
vector = [x₁, x₂, x₃, ..., xₙ]
```

where `n` is the embedding dimension.

Do not confuse:

```text
embedding dimension
```

with:

```text
number of documents
```

---

## 🧪 Lab

Generate embeddings for at least 20 sentences.

Group them manually into semantic categories.

Compare the numerical similarity with your human judgment.

# Chapter 03 — Vector Similarity & Distance

Retrieval depends on comparing vectors.

---

## 3.1 Cosine Similarity

Conceptually:

```text
similarity(A, B)
```

measures the angle between vectors.

---

## 3.2 Dot Product

Understand:

```text
A · B
```

and why vector magnitude can affect the result.

---

## 3.3 Euclidean Distance

Understand:

```text
distance(A, B)
```

as geometric distance.

---

## 3.4 Normalization

Study vector normalization and why normalized embeddings can make cosine similarity and dot product closely related.

---

## 3.5 Similarity Is Not Truth

Very important:

```text
high similarity
      ≠
factually correct
```

A retrieved document can be semantically similar but still irrelevant to the exact question.

A vector database stores and searches vectors efficiently.

---

## 4.1 Why Not Just Use Python Lists?

```text

```

a simple loop may be sufficient.

For:

```text
10 million vectors
```

brute-force comparison becomes expensive.

---

## 4.2 Vector Search

Conceptually:

```text
Query Vector
     ↓
Vector Index
     ↓
Nearest Neighbors
     ↓
Top K
```

---

## 4.3 Approximate Nearest Neighbor Search

Study the idea behind:

```text
ANN
```

Instead of checking every vector, an index efficiently searches likely candidates.

---

## 4.4 HNSW

Understand the high-level concept of:

> Hierarchical Navigable Small World graphs.

You do not need to implement HNSW from scratch.

Understand:

* graph-based search
* approximate search
* recall
* speed
* memory tradeoffs

---

## 4.5 Vector Database Options

Explore:

* PostgreSQL + pgvector
* Qdrant
* Chroma
* Pinecone
* Weaviate

Do not memorize APIs.

Understand architectural differences.

---

## 4.6 Database Selection

Consider:

* scale
* latency
* filtering
* operational complexity
* hosting
* cost
* existing infrastructure

# Chapter 07 — Chunking Strategies

This is one of the most important RAG chapters.

---

## 7.1 Why Chunk?

Documents are often too large to retrieve as a whole.

You want smaller units:

```text
Document
 ↓
Sections
 ↓
Chunks
```

---

## 7.2 Fixed-Size Chunking

Example:

```text
500 tokens
```

with overlap:

```text
50 tokens
```

Easy but not always semantically appropriate.

---

## 7.3 Sentence Chunking

Split by sentences.

---

## 7.4 Paragraph Chunking

Preserves natural structure.

---

## 7.5 Semantic Chunking

Split based on meaning or topic boundaries.

---

## 7.6 Recursive Chunking

Try larger structural boundaries first:

```text
document
 ↓
section
 ↓
paragraph
 ↓
sentence
```

---

## 7.7 Chunk Overlap

Why overlap exists:

```text
Chunk A
───────────────
         overlap
              ───────────────
              Chunk B
```

It helps prevent important context from being split exactly at the boundary.

---

## 7.8 Chunk Size Tradeoff

Small chunks:

* precise
* less context
* potentially incomplete

Large chunks:

* more context
* more noise
* fewer precise matches

---

## 7.9 Chunking Is a Retrieval Decision

Do not ask:

> "What chunk size is standard?"

Ask:

> "What unit of information should be retrievable for this application?"

---

## 🧪 Experiment

Create three versions of the same corpus:

```text

large chunks
```

Run the same evaluation questions.

Compare retrieval quality.


# Chapter 14 — Reranking

Initial retrieval is usually candidate generation.

Reranking performs a second, more expensive relevance assessment.

---

## 14.1 Two-Stage Retrieval

```text
Query
 ↓
Fast Retrieval
 ↓
Top 50 candidates
 ↓
Reranker
 ↓
Top 5
```

---

## 14.2 Why Not Rerank Everything?

Cost.

The first stage narrows the search space.

---

## 14.3 Bi-Encoder vs Cross-Encoder

Understand:

### Bi-encoder

Embeddings generated independently.

Fast retrieval.

### Cross-encoder

Query and candidate are considered together.

Usually more expensive but potentially more precise.

---

## 14.4 Reranking Tradeoff

```text
more retrieval candidates
        ↓
better recall
        ↓
more reranking cost
```

---

## 🧪 Experiment

Compare:

```text
vector top-5
vector top-20 → rerank → top-5
```

Measure whether the extra complexity improves evaluation results.

## 17.1 Basic RAG

```text

 ↓
Retrieve
 ↓
Context
 ↓

 ↓

```

---

## 17.2 Grounded Prompt

Tell the model:

* use provided context
* distinguish missing information
* avoid inventing unsupported claims
* cite sources where required

---

## 17.3 Context Delimiters

Separate:

```text
trusted instructions
```

from:

```text
retrieved untrusted content
```

Example:

```text

<retrieved_context>
...

...
```

---

## 17.4 "I Don't Know"

A good RAG system should be capable of saying:

> The provided documents do not contain enough information to answer this question.

This is often better than generating a confident unsupported answer.

# Chapter 19 — RAG Failure Modes

RAG systems can fail at many layers.

---

## Failure 1 — Bad Parsing

```text
PDF
 ↓
corrupted text
 ↓
bad chunks
 ↓
bad retrieval
```

---

## Failure 2 — Bad Chunking

Important information split across chunks.

---

## Failure 3 — Wrong Embedding Model

Semantic similarity becomes poor.

---

## Failure 4 — Retrieval Miss

Relevant document exists but isn't retrieved.

---

## Failure 5 — Retrieval Noise

Irrelevant documents are retrieved.

---

## Failure 6 — Context Overload

Too much irrelevant context is provided.

---

## Failure 7 — Model Ignores Context

The LLM generates an answer that isn't supported by retrieved information.

---

## Failure 8 — Stale Knowledge

The index contains an old document version.

---

## Failure 9 — Tenant Leakage

One customer's documents are retrieved for another customer.

---

## Failure 10 — Prompt Injection

A retrieved document contains malicious instructions.

---

## Failure 11 — Citation Failure

The answer cites the wrong source.

---

## Failure 12 — "No Answer" Failure

The system should have said:

```text
"I don't have enough information."
```

but generated an unsupported answer.

# Chapter 22 — RAG Security & Multi-Tenancy

This is critical for professional AI engineering.

---

## 22.1 Tenant Isolation

Imagine:

```text
Company A
 ├── documents

Company B
 ├── documents
```

Company A must never retrieve Company B's data.

---

## 22.2 Metadata Filters

Every retrieval request may need:

```text
tenant_id = current_user.tenant_id
```

---

## 22.3 Authorization Before Retrieval

Do not rely on the LLM to decide whether a document is accessible.

Your application must enforce authorization.

---

## 22.4 Document Poisoning

An attacker may intentionally insert malicious content into the knowledge base.

Study:

* poisoned documents
* malicious instructions
* hidden prompt injection
* misleading content

---

## 22.5 Secret Leakage

Do not allow retrieved content to expose:

* API keys
* credentials
* internal secrets
* unrelated customer data

---

## 22.6 Auditability

Record:

```text
user
query
retrieved document IDs
model
answer
timestamp
```

while respecting privacy requirements.

* potentially lower recall

The most important mental model from V10 is:

> **Retrieval determines what information the model gets to see. Generation determines how the model uses that information.**

A good LLM cannot compensate for consistently bad retrieval.

A good retriever cannot compensate for an application that blindly trusts model output.

A production RAG system therefore requires **both retrieval engineering and application engineering**.
